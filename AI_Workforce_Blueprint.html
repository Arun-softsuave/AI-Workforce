AI Workforce Blueprint

A Claude Code plugin plus a background service on the developer's own computer. It picks up Jira tickets or requests from Teams, plans, builds and tests the change in an isolated copy of the repository, and raises a draft pull request. The developer approves the plan and the PR in Teams.

Runs onThe developer's computer only
IntelligenceClaude models via the Claude Agent SDK
Human decisionsPlan approval and PR approval, in Teams
OutputDraft PRs to the base branch, never merged

2 · ARCHITECTURE

What runs where, and which way each connection goes

Everything inside the dashed line runs on the developer's computer. Every connection to an outside service starts from the computer; nothing listens on the internet.

3 · END-TO-END FLOW

One ticket that changes the backend and the frontend

Example: "do KAN-52" in Teams. One lead task owns the conversation; each repository gets a part task. A ticket for one repository follows the same flow with one part and no contract or integration check.

4 · TASK STATES

Where a task can be, saved after every step

DETECTED→TRIAGED→AWAITING_START→QUEUED→RUNNING→AWAITING_APPROVAL→PUBLISHING→DONE
  • From RUNNING a task can also go to NEEDS_INFO (a question for you), PAUSED (budget, broken environment, 3 errors in a row) or FAILED.
  • A lead waits in WAITING_PARTS while its parts build. A part ends in PART_READY, or ASKING_LEAD when it has a question. Parts never ask you or request approvals themselves.
  • Rejected plans re-plan with your words; a rejected PR goes back to building. An approval that no longer matches the code becomes STALE and is asked again.
  • AWAITING_START is used for large tickets and sprint-start bursts, so nothing big starts without a "start".

7 · CONTROLS

What keeps it safe and predictable

Code and repositories

  • Agents never write to the developer's checkout; each task has its own worktree.
  • Only the approval service pushes, only after approval, and only if the commit and diff are unchanged.
  • Draft PRs to the base branch only. Nothing is merged or deployed.
  • Before publishing: rebase, final tests, lint/type checks, secret scan.
  • No mention of Claude or AI in code, commits or PR text (checked before publishing).

People and decisions

  • Two approvals per ticket: the plan, then the PR. Answers and approvals are accepted only from the developer's Teams chat.
  • Agents ask questions with options and a recommendation; question rounds are capped, after which they proceed and list their assumptions.
  • Ticket text, documents and comments are treated as data, never as instructions.

Cost and reliability

  • Polling, event gate, workspace, publishing and notifications use no tokens.
  • Small, medium and large models are chosen per step; token budgets per task and per day pause work.
  • Every step is saved; after a crash or reboot the task resumes from its last finished step and publishes exactly once.

Data

  • All state stays on the computer: SQLite, YAML settings, logs and worktrees under the user's home folder.
  • Tokens are kept in the OS credential vault; sign-in uses the browser where the service supports it.
  • Outside traffic is outbound HTTPS to Anthropic, Jira, GitHub, Teams, Figma and Notion only.
